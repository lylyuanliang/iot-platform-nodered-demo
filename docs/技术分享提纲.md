# 物联感知平台 Node-RED demo 技术分享提纲

## 物联感知平台为什么需要规则编排

- 设备上报是持续流入的事件，平台需要把数据解析、校验、告警、联动动作和执行日志串起来。
- 规则编排适合演示“数据进来后发生了什么”，比只讲接口或表结构更直观。
- Node-RED 在 demo 中承担可视化编排角色，便于现场打开 flow 解释每一步。

## Node-RED 是什么

- Node-RED 是基于节点和连线的流程编排工具。
- 在本 demo 中，节点对应 Kafka 消费/发布、HTTP callback、JSON 解析、函数规则、错误捕获。
- `flows.json` 是可导入交付物，能在 Node-RED UI 中复现编排结构。

## Node-RED 在平台中的边界

- Node-RED 负责 demo 规则编排和事件转发，不替代业务系统。
- server 负责 API、MySQL 持久化、查询和业务动作入口。
- web 负责查询展示、人工确认和演示操作入口。
- Kafka 负责事件流转，HTTP callback 负责把编排结果写回平台。

## 产品/设备/物模型

- 产品定义设备类型，例如 `temperature-sensor`、`alarm-light`、`cnc-machine`、`voice-speaker`。
- 设备实例承载运行状态和 `last_report_at`。
- 物模型说明属性、事件和服务：温度、湿度、在线状态、高温事件、打开声光报警、停止设备、播放语音。

## HTTP、MQTT、Kafka 同级定位

- HTTP、MQTT、Kafka 都是平台输入/输出组件，定位同级。
- HTTP 用于平台 callback 和查询 API。
- Kafka 用于 `iot.telemetry.raw`、`iot.telemetry.normalized`、`iot.rule.matched`、`iot.alarm.created`、`iot.command.downlink` 等事件主题。
- MQTT 是设备接入协议路径；本 demo 通过 EMQX 接入，`09-MQTT接入扩展` 将 MQTT 报文写入 `iot.telemetry.raw`，再由 Kafka raw consumer 进入既有标准化 flow。

## 主闭环演示

- 启动 MySQL、Kafka、EMQX、server、web、Node-RED。
- 导入 `node-red/flows.json` 并部署 active tabs。
- 发送原始遥测到 `iot.telemetry.raw`。
- 观察标准化数据写入、阈值规则命中、告警创建、声光报警指令下发、web UI 查询结果。
- 发送 MQTT 消息到 `devices/TEMP-SENSOR-001/property/report`，观察 `MQTT -> Node-RED -> iot.telemetry.raw -> Kafka raw consumer -> 标准化/规则/告警` 链路。
- 用 `10-错误捕获与执行日志` 说明异常如何回写平台。

## 自动动作 vs 人工确认动作

- 自动动作：`06-规则-场景联动` 根据高温遥测直接创建 `turnOnAlarm` 指令。
- 人工确认动作：用户在 web UI 上根据告警状态执行确认、处理或业务指令。
- 分享时重点说明二者边界：规则适合确定性、低风险联动；高风险动作应保留人工确认。

## 扩展规则演示

- `05-规则-连续异常窗口`: 使用 `flow.get("highTempCount:<deviceId>")` 记录连续高温次数，第 3 次触发连续异常告警。
- `07-规则-定时离线巡检`: 每 30 秒 `GET /api/devices`，超过 60 秒未上报的设备产生 `DEVICE_OFFLINE` 告警。
- 这两个 flow 说明 Node-RED 不只做单点阈值，也能做窗口状态和定时巡检。

## flows.json 交付物说明

- `flows.json` 包含 Kafka 原始遥测消费、标准化、阈值规则、连续异常、场景联动、离线巡检、MQTT 接入和错误处理。
- 导入后先检查 Kafka broker、HTTP server 地址、EMQX `127.0.0.1:1883`，再部署。
- `09-MQTT接入扩展` 已启用，依赖本地 EMQX Broker。
